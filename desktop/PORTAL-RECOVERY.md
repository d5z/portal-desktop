# Portal 启动和断连恢复

以下说明对应当前源码。先在右上角菜单确认客户端版本；从 0.1.1 的 Squirrel 安装迁移到 NSIS 时，旧快捷方式可能仍指向旧客户端，迁移步骤见 [配套更新](UPDATING.md)。

## 免重启恢复

1. 打开「本机 Portal」。如果只是不显示最新聊天，可以先「刷新 Being 对话」；这个按钮重载聊天页，不会重启本机引擎。
2. Portal 长期「重连中」或进程已经退出时，先保存当前工作，再点击「重启 Portal」。它会停止客户端管理的引擎及其守护，再按原来的后台常驻设置启动，会中断当前工具任务。显示「未启动」时使用「启动 Portal」。
3. 若显示凭据、目录、权限或实例冲突错误，先处理具体错误。达到连续失败上限后，点击启动会重置失败标记和次数。重新打开客户端也会重试已启用但退出的后台服务；用户主动停用的服务不会因此重新启用。
4. 如果应用本身无响应，先尝试退出客户端，再从开始菜单或桌面快捷方式打开。不要只关闭窗口：关闭窗口的正常行为是隐藏到托盘。不要删除配置或按名称批量终止所有 Portal。
5. 仍无法恢复时，使用「打开日志文件夹」保留诊断文件，或「一起看日志」将脱敏日志放入对话草稿，再由用户决定发送。记录故障时间、客户端版本、Portal 状态以及恢复操作。

Windows 日常使用建议从安装器创建的快捷方式启动。`npm start` 或终端直接启动属于开发/命令行启动；关闭终端可能结束其关联的客户端。已启用的独立计划任务与可见终端分开管理。

## 日志与实例位置

- 当前 profile 的 `portal-service.json` 指向客户端管理的后台运行目录。Windows 通常位于 `%APPDATA%\portal-desktop`；旧配置可能继续使用 `%APPDATA%\Beings`，自定义 profile 则以实际配置为准。
- 后台状态只读取该运行目录中的 `pid`、`.portal-status-nonce`、`.portal-connection-status.json` 和 `.portal-ready.json`；同时核对计划任务、可执行路径、PID 和本次启动标识。它不会从其他目录挑选一个看起来较新的 ready 文件。
- `portal-service` 中多个 UUID 目录可能是升级保留的旧运行目录，不等于多个活跃引擎。旧目录还可能保存正在使用的自定义 TOML，不能一律删除。独立脚本创建的 Portal 属于另一套管理入口。
- Electron 正常运行也有多个进程；不能仅凭“有 5 个客户端进程”认定为僵尸。需要区分主进程、renderer/GPU 等子进程，核对完整可执行路径及配置目录。
- Windows `supervisor.log` 记录启动、PID、退出码、存活时长、重试及暂停原因；`supervisor.err.log` 覆盖凭据解密、工作目录和引擎启动错误。两者按大小轮转并保留 `.previous`；引擎输出也保留上一轮 `.previous`。界面日志和日志引用包含最近的守护记录与上一轮引擎错误，并脱敏。
- 「一起看日志」包含实际运行目录和 PID。日志目录中的 `portal-status.json` 还包含后台状态和运行目录，便于确认读取的是哪一个实例。

## 对 2026-09-17 Eureka 反馈的核查

| 请求 | 源码核查和处理 |
| --- | --- |
| R1 失败标记清理 | v0.1.3 源码已有 `BackgroundPortal.load → resetRecovery`。发现同版本启动恢复路径可能跳过已启用但退出的任务，已补上。保留连续失败上限和冲突保护；重启电脑并不会自动删除磁盘上的标记。 |
| R2 启动失败留痕 | 修复 Windows runner 初始化在异常捕获之外的问题；记录退出码，追加守护日志并保留上一轮引擎错误，接入日志引用。 |
| R3 手动恢复 | 增加「重启 Portal」，覆盖启动中、重连中及错误状态，保留后台常驻偏好。引擎本身已有 Relay 重连循环；仅凭远端错误字符串，不能判定是哪一层失去连接。 |
| R4 多目录与进程 | 沿用当前 profile 的运行记录作为后台状态来源，在诊断引用中补充目录/PID。保留依赖旧目录的配置；仅通过既有实例归属检查处理冲突，不批量杀进程或删目录。 |
| R5 终端关联退出 | 补充快捷方式启动说明，区分开发终端和独立后台计划任务。 |

这些改动覆盖已确认的客户端缺口，不证明已还原报告机器的全部根因。需要故障当时的运行记录、进程身份和日志才能判断历史崩溃；“幻影 tool_call”、记忆编码和自主唤醒应单独凭工具调用/事件记录排查，不能与本机启动故障合并归因。
